# RC1: навантаження (S3-10)

Стенд: `flowi-server-app/ops/load/`. Прогін 2026-11-22 на гілці `release/rc1`
(`acd3c09` плюс незакомічені правки паралельних агентів). Реально прогнано:
S і M на Postgres, S на SQLite (sync і concurrent_edit) та S/concurrent_edit на 2 vCPU.
L **не прогнаний**.

## Що в комплекті

| Файл | Призначення |
|---|---|
| `ops/load/docker-compose.staging.yml` | Postgres 16 + Redis 7 + Daphne (той самий Dockerfile), ліміти CPU/RAM; профіль `sqlite` — дзеркало поточного проду; профіль `k6` — генератор `grafana/k6:0.54.0` |
| `ops/load/load_settings.py` | прод-settings + `LOAD_CONN_MAX_AGE` (єдиний оверрайд; Postgres/Redis settings.py вже вміє через `DATABASE_URL`/`REDIS_URL`) |
| `ops/load/seed_dataset.py` | датасети S/M/L, пише через `apply_project_mutations`/`apply_user_mutations`, перевіряє кількість рядків і cursor, мінтить токени (без логіну: `auth`-тротлінг 20/год) |
| `ops/load/k6/{sync,lists,invites,concurrent_edit}.js` | сценарії, перевіряють тіло відповіді, а не лише статус |
| `ops/load/run.sh` | повний прогін: build → seed → кожен сценарій на чистому процесі сервера → семпли `pg_stat_activity`, лог lock waits, 5xx/429 → `out/<run>/report.md` → `down -v` |
| `ops/load/summarize.py`, `report.template.md` | генерують звіт прогону |

Запуск: `cd flowi-server-app && ops/load/run.sh -p "S M" -d 40s -c 0`
(`-c 600` = CONN_MAX_AGE як у проді; `--keep` не гасить стенд). Потрібен лише Docker.
Результати лежать в `ops/load/out/` (у `.gitignore`: там живі токени стенду).

## Припущення про прод

- Специфікацій VPS (159.89.99.91) у репозиторіях і пам'яті немає. **Припущення: 1 vCPU / 2 GB.**
  Бюджет поділено на весь стек: server 0.60 CPU / 1152 MiB, Postgres 0.30 / 640 MiB,
  Redis 0.10 / 128 MiB (разом 1.0 CPU / 1.9 GiB). Ліміти перевірено через `docker inspect`.
  **Власнику:** підтвердити реальні vCPU/RAM (`nproc; free -m`) і за потреби
  перевизначити `SERVER_CPUS`/`PG_CPUS`/… та повторити прогін.
- **Прод зараз на SQLite WAL + один Daphne без Redis** (perf pass 2026-11-06).
  Стенд міряє цільову Postgres+Redis топологію. Тож розмір пілоту нижче чинний
  **лише після переїзду проду на Postgres+Redis** з виправленням з'єднань (див. F1/F2).
  Профіль `sqlite` у compose є, але в цьому прогоні не міряний.
- Пошти на стенді бути не може: `EMAIL_USER` порожній, хост 127.0.0.1:1, адреси `@load.example.invalid`.

## Сценарії (1 VU = 1 користувач, темп нижче за тротлінг)

- **sync**: `/sync/user/v2/` плюс `/projects/{id}/sync/` для кожного проєкту кожні ~3 с.
  Перша ітерація — холодний pull. Учасник у ~30% ітерацій змінює статус своєї задачі.
- **lists**: проєкти, деталі, учасники, активність, my-work, workload (лише менеджери),
  invites/mine, notifications, unread-count кожні ~2 с.
- **invites**: власник створює link-інвайт (max_uses=1), новий користувач приймає його,
  потім читається список інвайтів (5 VU, shared-iterations).
- **concurrent_edit**: 2 пристрої на користувача (VU = 2×учасники) правлять задачі спільного проєкту
  з `base_revision`. Менеджери правлять «гарячі» задачі, виконавці свої. Пауза ~1 с.
- Не покрито: WebSocket fan-out, `/workspace/` і `/invites/preview/` (тротлінг per-IP, а k6 працює з одного IP).

## Режими відмови (знайдено)

- **F1. Витік з'єднань з Postgres при CONN_MAX_AGE=600 під Daphne.** Кожен запит ASGI виконується
  у власному потоці (`ThreadSensitiveContext`), і постійне з'єднання лишається за цим потоком.
  Прогін A (10 VU): conn max 58 при `max_connections=60`, далі `FATAL: sorry, too many clients already` → 500.
  Повторено й на 2 vCPU (S/concurrent_edit, CONN_MAX_AGE=600): 13 відповідей 500 з тією ж причиною.
  **Fix (server owner):** у `settings.py` для ASGI ставити `conn_max_age=0`
  (або пул: psycopg3 `OPTIONS.pool` / pgbouncer). Поки прод на SQLite, цей баг не проявляється.
  Проявиться одразу після переходу на `DATABASE_URL`.
- **F2. Необмежена конкурентність запитів → вичерпання з'єднань навіть при CONN_MAX_AGE=0.**
  Daphne не обмежує кількість одночасних sync-view, і кожен з них тримає своє з'єднання.
  На M/concurrent_edit 100 одночасних записів у проєкт чекали на лок → 61 з'єднання → 1 134 відповіді 500.
  **Fix:** pgbouncer (transaction pooling) перед Postgres або обмеження конкурентності
  (кілька процесів Daphne за Caddy з малим пулом потоків), плюс `max_connections` під це.
- **F3. Серіалізація записів у проєкт на рядковому локу.** Кожен `/projects/{id}/sync/` з мутаціями
  бере `SELECT … FROM core_project … FOR UPDATE` і тримає лок усю транзакцію: перевірка політики,
  активність, сповіщення. Найповільніші запити в лозі Postgres — саме цей `FOR UPDATE` (до 6 с на S).
  Одночасне редагування одного проєкту масштабується погано: S (20 пристроїв) — p95 ≈ 3–4 с,
  M (100 пристроїв) — p95 12–14 с. Дедлоків немає, конфлікти ревізій коректні.
  Дуже чутливо до CPU Postgres: лок тримається через кілька round-trip до БД, а Postgres
  має лише 0.3 CPU. Той самий S/concurrent_edit дав p95 0.7 с при 1.0+1.0 CPU
  і 52–68 мс на SQLite з 1.0 CPU (див. таблицю C).
- **F4. Плато пропускної здатності ≈ 17–18 запитів/с на читанні і ≈ 13 запитів/с на sync** (server 0.6 + PG 0.3 CPU).
  lists на S і M дають однакові 17.1 і 18.2 RPS, але p95 зростає з ~0.9 с до 4–6 с. Отже, S уже стояв біля стелі.
  Плато узгоджується з CPU-квотою, але **CPU під час прогону не семплувався**: `docker stats` знімається після k6,
  тож у звітах там простій. Пам'ять не обмежує: сервер < 190 MiB, Postgres < 70 MiB.
- **F5. Масовий запис нормальний:** після прибирання хешування паролів S (2 550 мутацій плюс flush)
  сидиться за 12 с на Postgres і за 5 с на SQLite. Попередня оцінка «45–60 мутацій/с» була хибною:
  час з'їдав PBKDF2.
- **F6. Інвайти не є вузьким місцем** (p95 < 0.7 с). Але лист надсилається всередині запиту
  (`EMAIL_TIMEOUT`, типово 10 с): повільний relay безпосередньо збільшує латентність email-інвайту.
  Цей прогін створював лише link-інвайти.
- `rejected` у concurrent_edit (3–10 на прогін) — усі `forbidden_task_fields`, перевірено в `ProjectSyncMutation`.
  Це артефакт сценарію: k6-виконавець шле записаний при сидингу `title`, а менеджер його вже змінив.
  Тож учасник «змінює» title, а це заборонене поле. Сервер поводиться правильно. Реальний клієнт бере `data` з pull.

## Підтримуваний розмір пілоту

Ємність вимірюється в запитах/с, а не у VU: VU сценаріїв значно агресивніші за людей
(lists ≈ 1.7 запиту/с на VU, sync ≈ 0.9). Плато (F4): ~17 запитів/с на читанні, ~13 на sync
при прийнятному p95 < 1 с лише до ~15 запитів/с. Припущення щодо реального користувача
із застосунком у фокусі: ~1 запит на 5–10 с (sync при фокусі/зміні, відкриття екранів), тобто 0.1–0.2 запиту/с.
Це оцінка, а не вимір. Перерахунок: 15 / 0.1–0.2 ≈ 75–150 одночасно активних користувачів на чисте читання і sync.

Рекомендація для 1 vCPU / 2 GB (Postgres+Redis — лише після фіксу F1 і F2; SQLite — як зараз):

- **Пілот: 1 воркспейс, до ~30 учасників**, одночасно активних ≤ ~20. Запас ~3× від оцінки вище,
  бо WebSocket, сповіщення, воркер і Caddy не навантажувались, а per-user rate — припущення.
- **Одночасне редагування одного проєкту — головний ризик (F3).** На Postgres 0.6/0.3: ≤ ~10 пристроїв,
  що активно пишуть (p95 ~3 с на 20). На SQLite або з більшою часткою CPU для Postgres — суттєво краще (таблиця C).
- **50+ одночасно активних і сплески запису в один проєкт** потребують F1+F2, ≥ 2 vCPU і повтору M/L.
- **Не переводити прод на Postgres без фіксу F1**: це гарантовані 500 вже на десятці користувачів.

## Застереження

Docker Desktop на Mac (8 ядер arm64): CPU quota відтворює частку CPU, але не диск VPS і не архітектуру.
Статичний поділ CPU між контейнерами консервативніший, ніж спільне ядро на VPS.
Одночасно на машині працювали інші агенти, тож абсолютні числа шумні. Відносні висновки (F1–F4) стабільні.
k6 ділив з сервером той самий хост. Перед кожним сценарієм сервер перезапускався.
WebSocket не навантажувався.

## Протокол для власника / наступного прогону

1. Підтвердити специфікації VPS. Якщо вони відрізняються, експортувати `SERVER_CPUS`/`SERVER_MEM`/`PG_CPUS`/`PG_MEM`.
2. Після фіксу F1 (і F2, якщо робиться) у server: `ops/load/run.sh -p "S M" -d 60s -c 0`.
   Очікування: 0 "too many clients", M/concurrent_edit без 5xx.
3. L (200): `ops/load/run.sh -p L -d 60s -c 0`. Сидинг тепер без хешування паролів; час не міряний.
4. Поточний прод (SQLite): стенд має `server-sqlite` (порт 18081, профіль `sqlite`).
   Seed: `docker compose -p flowi-load -f ops/load/docker-compose.staging.yml --profile sqlite up -d server-sqlite`,
   потім `exec server-sqlite python ops/load/seed_dataset.py --profile S --reset --out ops/load/out/dataset-S.json`
   і k6: `docker compose … --profile k6 run --rm -T k6 run -e BASE=http://server-sqlite:8000 -e DATA=/load/out/dataset-S-sqlite.json /load/k6/sync.js`.
   Так виконано для S (таблиця C). `run.sh` поки ганяє лише Postgres-варіант. Для чистого SQLite-прогону зупиніть Postgres-`server`.
5. Після релізу: `MIN_MOBILE_VERSION=1.4.0` не впливає на навантаження. k6 шле `X-Flowi-Client: mobile/1.4.0 (ios)`.

| Перевірка | Як | Критерій |
|---|---|---|

| Датасет консистентний | seed перевіряє рядки й cursor | exit 0 |
| Без витоку з'єднань | `conn max` у звіті, "too many clients" | ≤ max_connections, 0 |
