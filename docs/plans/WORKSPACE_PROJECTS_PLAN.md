## §0 Базовий стан + контракт
- Зафіксувати наявні помилки перевірок ДО змін (mobile: `npx tsc --noEmit`,
  `npx eslint`, `npx jest`; web: `npx tsc --noEmit`, `npm run lint`, тести якщо є;
  server: `python manage.py test`, `makemigrations --check`). Нові помилки після
  фаз = регресія.
- Написати `WORKSPACE_PROJECTS_CONTRACT.md`: ендпоінти, payload-и, коди помилок,
  WS-канали, формати sync для §2–§4.

## §1 Сайдбар планшета (Особисте) = веб
На планшеті (NavSidebar, `constants/nav.ts`) пункти й групування мають
повторювати веб (`flowi-web-app/app/app/layout.tsx` NAV_GROUPS):
- **Робота**: Огляд(Сьогодні), Задачі, Проєкти, Наради, Час, Нотатки
- **Особисте**: Фінанси, Бюджет, Підписки, Скарбнички, Здоров'я
- **Ще** (згортається): Зведення здоров'я, Профіль здоров'я, Профілактика,
  Тренування, Контейнери
- **Розробка** (згортається): Ідеї та баги, Агент
- Внизу, як і було: Налаштування (+ інші службові пункти, що є на мобільному, але
  не мають веб-аналога — в «Ще»). Порядок і назви — як у вебі (через i18n).
Маршрути — мобільні відповідники; пункта без мобільного екрана не вигадувати.

## §2 Workspace
- **Workspace = сервер.** У UI — «Workspace». Один workspace за раз.
- **Старт застосунку:** обов'язковий екран «Адреса workspace» (автозаповнено
  Flowi Cloud `https://api.flowi.casperdev.site`) → перевірка → вхід/реєстрація.
  Без входу застосунок недоступний.
- **Режим «Розпочати офлайн» прибирається.** «Офлайн» = лише тимчасова відсутність
  мережі; дані локально + outbox, синк після появи мережі.
- **Міграція офлайн-користувачів:** після оновлення — екран workspace → вхід.
  Локальні дані зберігаються й після входу вивантажуються в акаунт; якщо в
  акаунті вже є дані — діалог «злити з акаунтом».
- **`GET /api/workspace/`** (публічний): назва, колір/лого, версія
  sync-контракту, мінімальна версія клієнта, режим реєстрації, WS-адреса.
  Несумісна версія → зрозуміла помилка «оновіть сервер/застосунок».
- **Зміна workspace = вихід:** якщо outbox не порожній — попередження + спроба
  досинхронізувати; далі очистка локальних даних, токенів, курсорів. Дані
  одного сервера ніколи не потрапляють на інший.
- **Реєстрація:** режим — налаштування workspace: `open` | `approval`.
  Self-host стартує в `approval`; Flowi Cloud — `open`. Перший зареєстрований
  користувач стає адміном workspace. У режимі `approval` форма реєстрації
  створює заявку; адмін погоджує/відхиляє **у застосунку** (Налаштування →
  Адміністрування workspace, мобільний і веб), отримує push про нову заявку;
  заявник бачить екран очікування і дізнається про рішення (push/екран).
  Адмін також бачить список користувачів і перемикає режим реєстрації.
- **Веб:** один веб для всіх workspace — теж крок «адреса workspace»
  (зберігається в localStorage), API/WS з обраної адреси. Сервер за
  замовчуванням дозволяє CORS для офіційного вебу (+ env). Авторизація —
  bearer-токени (без cross-site cookies).
- **Self-host:** docker-compose «в один рядок»: server + Postgres + Redis
  (`channels_redis` замість InMemoryChannelLayer, коли задано REDIS_URL) +
  Caddy з авто-HTTPS; `.env.example` (домен, назва workspace, режим
  реєстрації, секрети); workflow збірки образу в GHCR; інструкція в README.

## §3 Простір проєкту (соло; модель готова до команди)
- **Вхід у проєкт = повна зміна контексту.** Телефон: нижні таби замінюються
  табами проєкту, у шапці свічер проєкту. Планшет/веб: сайдбар стає сайдбаром
  проєкту з «← Особисте» вгорі і свічером. Після перезапуску — завжди
  Особисте; свічер пам'ятає нещодавні проєкти.
- **Розділи проєкту:** Огляд, Завдання (Дошка / Список / Календар / Таймлайн),
  Наради, Нотатки, Час, Бюджет, Спринти, Налаштування. Огляд і Завдання —
  завжди; решта вмикається/вимикається в налаштуваннях проєкту. Шаблони при
  створенні: «Робочий» (усе) / «Простий» (лише завдання).
- **Огляд** — дашборд: прогрес і дедлайн, прострочене, найближчі наради,
  поточний спринт, години за тиждень, витрачено з бюджету.
- **Статуси:** власний workflow на проєкт (створюється копією глобальних).
  Кожен статус має тип `todo | in_progress | done`, щоб «Сьогодні»
  агрегував.
- **Таймлайн/Гант:** нове опційне поле завдання `startDate`; без нього смуга =
  дата створення → дедлайн; тягнення країв змінює дати (планшет/веб; телефон —
  перегляд + редагування дат у картці).
- **Належність:** один опційний `projectId` у записі — tasks, meetings, notes,
  time_entries, transactions (підписки вже мають).
- **Особисте агрегує:** «Сьогодні» і «Завдання» показують моє з усіх проєктів
  з міткою проєкту.
- **Сервер одразу:** моделі `Project`, `ProjectMember` (роль), `ProjectItem`
  (project, collection, local_id, data, revision, change_seq, deleted) —
  та сама механіка outbox/курсор/конфлікти, що й sync v2, але курсор на
  проєкт і WS-канал `ws/project/{id}/`. Клієнт синкає особистий простір + усі
  свої проєкти. Локально записи в тих самих ключах (`tasks`, …) — агрегація
  працює сама. Наявні проєкти й записи з projectId мігрують з UserItem у
  простір проєкту (серверна міграція + клієнтська маршрутизація outbox).
- Без мережі все працює локально, синк пізніше.
- **Веб — паритет:** сайдбар проєкту, URL `/app/p/{id}/overview|board|list|calendar|timeline|meetings|notes|time|budget|sprints|settings`.

## §4 Команда
- **Ролі:** Власник (налаштування, учасники, видалення, бюджет) / Учасник
  (створює й редагує все, крім бюджету) / Глядач (читає, коментує).
- **Бюджет бачить лише власник:** транзакції з projectId і розділ Бюджет
  доступні тільки власнику (сервер фільтрує, клієнт ховає розділ).
- **Запрошення:** посилання (роль + термін дії) або email наявного акаунта.
  Посилання несе адресу workspace і проєкт (deep link `ftrackingapp://invite?...`
  + веб-URL). Без акаунта → застосунок підставляє workspace → заявка на
  реєстрацію з позначкою «запрошений у проєкт X користувачем Y»; після
  погодження адміном — одразу учасник.
- **Виконавці** (`assigneeId`) + у «Сьогодні»/«Завдання» — призначене мені.
- **Коментарі та @згадки** у завданнях і нарадах.
- **Стрічка активності** проєкту (хто що змінив).
- **Push:** призначили мені, згадали, змінили статус мого завдання, нова
  заявка (адміну), рішення по заявці. Сервер шле через Expo Push API;
  клієнт реєструє push-токен.
- **«Спільне» зливається в проєкти — жорсткий перехід:** кожна група стає
  проєктом («Простий» шаблон) власника-творця (перший учасник з акаунтом);
  секції → групи/колонки, пункти → завдання; решта учасників приєднуються
  заново за запрошенням. Старі ендпоінти груп і `ws/group/` вимикаються
  (410 Gone), екран «Спільне» прибирається з навігації (плитка на
  «Сьогодні» теж).
